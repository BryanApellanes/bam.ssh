# bam.ssh Decision Log

Records *why* decisions were made, not just what they are. Append-only; newest entries at the bottom.

## D-001: Core libraries have zero dependencies outside this repository

**Date:** 2026-07-15
**Decision:** `bam.ssh.common` through `bam.ssh.server` reference only each other. No bamtk framework references, no third-party packages in the core (BouncyCastle admitted only if a required algorithm has no BCL equivalent — see D-004). Only `bam.ssh.tests` references bamtk projects (`bam.test`, `bam.console`).
**Why:** Native AOT + trim-safety across five OSes is a hard requirement; every dependency is a compatibility risk. It also keeps the stack suitable for standalone open-source publication while still building inside `bamtk.sln`.

## D-002: Root namespace `Bam.Ssh` is owned by `bam.ssh.common`; top-level API types also live in `Bam.Ssh`

**Date:** 2026-07-15
**Decision:** The common/primitives assembly uses root namespace `Bam.Ssh` (not `Bam.Ssh.Common`). The flagship API types `SshClient` and `SshServer` are declared in namespace `Bam.Ssh` even though they compile into `bam.ssh.client` / `bam.ssh.server`. Layer-specific types live in `Bam.Ssh.Transport`, `Bam.Ssh.Authentication`, `Bam.Ssh.Connection`, etc.
**Why:** Mirrors BCL idiom (e.g. `HttpClient` in `System.Net.Http`): application developers get the whole developer-facing surface with a single `using Bam.Ssh;`, while protocol internals stay in layer namespaces. C# namespaces may span assemblies, so this costs nothing.

## D-003: Strict layering enforced by project references

**Date:** 2026-07-15
**Decision:** Project references encode the directive's layering exactly: transport → common; authentication → transport; connection → authentication; sftp/scp → connection; terminal → common; client/server → connection + sftp + scp + terminal. No project may reference upward or sideways beyond this.
**Why:** Making the layering a compile-time property (rather than a convention) means a violation is a build error, not a review finding.

## D-004: BCL cryptography first; BouncyCastle only for gaps

**Date:** 2026-07-15
**Decision:** All cryptography uses `System.Security.Cryptography` where the BCL provides the algorithm. Known BCL coverage: X25519/Ed25519 (`System.Security.Cryptography` net10 has `X25519`/`Ed25519` support — verify at Phase 3; fall back to BouncyCastle 2.6.x if absent on any target platform), ECDH P-256, DH group14 via `BigInteger` or BouncyCastle, AES-GCM (`AesGcm`), AES-CTR (composed from `Aes` ECB + counter, since BCL has no CTR mode), ChaCha20-Poly1305 (`ChaCha20Poly1305` — note: OpenSSH's `chacha20-poly1305@openssh.com` uses a two-key construction that requires a raw ChaCha20 keystream, which the BCL does NOT expose; this will need a managed ChaCha20 implementation or BouncyCastle — decide at Phase 4), HMAC-SHA2, SHA-2 family, `RandomNumberGenerator`.
**Why:** The directive mandates .NET primitives where feasible with BouncyCastle as the documented fallback. bam.encryption already depends on BouncyCastle 2.6.2, so precedent exists in the toolkit if needed.

## D-005: Test project uses bam.test/bamtest (not xUnit)

**Date:** 2026-07-15
**Decision:** `bam.ssh.tests` is a console exe on the bamtk `bam.test` framework (`UnitTestMenuContainer`, `[UnitTest]`), discovered by the bamtk `run-tests.sh`/`bamtest` orchestrator, per the toolkit-wide convention. Confirmed by project owner 2026-07-15.
**Why:** Toolkit consistency; bamtest aggregates coverage across the whole bamtk solution. The core libraries stay framework-free (D-001), so this does not affect AOT goals.

## D-006: Compression negotiated but deferred

**Date:** 2026-07-15
**Decision:** The transport advertises and accepts only `none` compression initially. The negotiation and packet pipeline include the seam for `zlib`/`zlib@openssh.com` (payload transform between framing and encryption), but no compressor ships until a later pass.
**Why:** Compression is optional in RFC 4253, rarely beneficial on modern links, and `zlib@openssh.com` (delayed compression) adds auth-state coupling. Deferring it keeps Phase 2–4 focused; the seam prevents a later retrofit.

## D-007: `System.Diagnostics.DiagnosticSource` (ActivitySource) is the one non-BCL-core assembly admitted to the core libraries

**Date:** 2026-07-15
**Decision:** The core libraries stay dependency-free (D-001) with a single exception: `System.Diagnostics.DiagnosticSource`, used for `ActivitySource`/`Activity` tracing spans (`SshActivitySource` in `bam.ssh.common`). Logging uses the framework-free `ISshLogger` seam instead of any logging package.
**Why:** The directive explicitly requires `ActivitySource` and OpenTelemetry support. `System.Diagnostics.DiagnosticSource` ships in the .NET shared framework, is trim/AOT-annotated by Microsoft, and needs no `PackageReference` (it resolved at build with `IsAotCompatible`/`TreatWarningsAsErrors` on and zero warnings). Re-implementing tracing would be strictly worse than consuming the first-party, AOT-safe primitive. A logging *framework* (e.g. bamtk `bam.logging`) would break AOT/portability, so logging is abstracted behind `ISshLogger` and adapted only in the future client/server composition roots.

## D-008: Cipher applied around framing via a per-direction `ISshPacketCipher`; sequence numbers owned by the reader/writer, not the codec

**Date:** 2026-07-15
**Decision:** Encryption/MAC is a per-direction seam (`ISshPacketCipher`) that the Phase 2 `SshPacketWriter`/`SshPacketReader` apply around the Phase 1 encoder/decoder. `NonePacketCipher` is the cleartext identity used before key exchange. The seam exposes `Geometry` (drives padding), `MacLength`, `LengthPeekSize`, `TransformOutgoing`, `DecryptLength`, and `VerifyAndDecrypt` — enough for Phase 4's chacha20-poly1305 (encrypted length, 16-byte tag), AES-GCM (cleartext length, 16-byte tag), and AES-CTR+HMAC (cleartext length, separate MAC) without touching the send/receive loop. The send/receive `SshSequenceNumber` lives in the writer/reader (not the Phase 1 codec) because the MAC binds the sequence number to cipher state.
**Why:** Keeps framing, ciphering, and orchestration at one responsibility each and makes the Phase 4 swap a field assignment (`SwapCipher`/`ApplyKeys`) rather than a rewrite. The returned `SshIncomingPacket` owns a pooled copy of the payload (via the Phase 1 `SshRentedBuffer`) because the decoder's slice is only valid until the pipe advances — pooled, not `new byte[]`, to hold the near-zero-allocation line.

## D-009: BouncyCastle admitted to `bam.ssh.transport` for X25519 and Ed25519 only

**Date:** 2026-07-15
**Decision:** `BouncyCastle.Cryptography` 2.6.2 is referenced by `bam.ssh.transport` (Phase 3), used in exactly two places: `Curve25519KeyExchange` (X25519 agreement for curve25519-sha256) and `Ed25519HostKey` (ssh-ed25519 signature verification). Everything else cryptographic uses `System.Security.Cryptography`: `ECDiffieHellman` (ecdh-sha2-nistp256), `BigInteger` (diffie-hellman-group14-sha256, RFC 3526 group 14), `ECDsa` (ecdsa-sha2-nistp256 host keys), `RSA` (rsa-sha2-256/512 host keys), and the SHA-2 family. This is a documented, narrowly-scoped exception to D-001 (zero external dependencies in core libraries).
**Why:** Probed on the target machine: .NET 10's BCL exposes `ECDiffieHellman`, `AesGcm`, `ChaCha20Poly1305`, and `MLKem` but **no X25519 and no Ed25519**. The directive *requires* curve25519-sha256 and Ed25519, so the D-004 BouncyCastle fallback is unavoidable for those two primitives. BouncyCastle 2.6.x is pure-managed, reflection-free in these code paths, and Native AOT / trim compatible; `bam.encryption` already depends on the same package version. Confining the reference to `bam.ssh.transport` (which the directive designates as the home of key exchange and packet encryption) keeps the rest of the stack BCL-only. Note for Phase 4: OpenSSH's `chacha20-poly1305@openssh.com` uses a two-key construction requiring a raw ChaCha20 keystream that the BCL `ChaCha20Poly1305` does not expose, so that cipher will also need BouncyCastle (or a managed ChaCha20) — to be decided in Phase 4.

## D-010: Phase 3 produces key material; cipher activation and host-key trust are deferred

**Date:** 2026-07-15
**Decision:** `SshClientKeyExchange.PerformAsync` completes the full handshake (KEXINIT negotiation, agreement, signature verification, NEWKEYS) and returns `SshKeyExchangeResult` carrying the negotiated algorithms, the verified host key, the exchange hash, and `SshSessionKeys`. It does **not** call `SshTransport.ApplyKeys` — turning `SshSessionKeys` into live ciphers is Phase 4 — and it does **not** decide host-key *trust* (known_hosts/TOFU), only that the signature is cryptographically valid; trust policy is Phase 7. Keys are derived at a uniform 64-byte length; because RFC 4253 §7.2 derivation is a prefix relationship, Phase 4 slices the exact prefix each negotiated algorithm needs.
**Why:** Phase boundaries. Phase 3 owns the cryptographic handshake; Phase 4 owns ciphers; Phase 7 owns the client trust model. Surfacing the verified key and hash (rather than silently accepting or activating) keeps each concern in its phase without hiding the trust decision.

## D-011: chacha20-poly1305@openssh.com uses BouncyCastle; aes-ctr is composed from BCL Aes-ECB; ciphers activate at NEWKEYS

**Date:** 2026-07-16
**Decision:** Phase 4 ships three cipher families as per-direction `ISshPacketCipher` implementations built by a static `SshCipherFactory` and installed by `SshClientKeyExchange` via `SshTransport.ApplyKeys` immediately after SSH_MSG_NEWKEYS. Crypto sources: `chacha20-poly1305@openssh.com` uses **BouncyCastle** `ChaChaEngine` + `Poly1305` (its two-key construction encrypts the length with a second ChaCha20 key and derives the Poly1305 key from block 0 of the payload keystream — the BCL `ChaCha20Poly1305` AEAD cannot express this); `aes256/128-gcm@openssh.com` uses the BCL `AesGcm`; `aes256/128-ctr` is composed from the BCL `Aes` ECB primitive as a counter-mode keystream (the BCL has no CTR mode) paired with an `IncrementalHash` HMAC-SHA2 (`hmac-sha2-256`/`512`). `ISshPacketCipher.DecryptLength` gained a `sequenceNumber` parameter (chacha20-poly1305 keys the length cipher on it). `aes128-ctr` was added to the advertised catalog. Rekeying (`RekeyAsync`) re-runs the exchange preserving the first exchange's session id; automatic rekey *scheduling* and mid-rekey data handling are deferred to the connection layer (Phase 6/7).
**Why:** This is the concrete resolution of the Phase 4 question flagged in D-004/D-009. BouncyCastle is already admitted to `bam.ssh.transport` (D-009) and is the only pure-managed, AOT-safe way to get OpenSSH's two-key ChaCha20 construction; everything the BCL covers (AES-GCM, AES-ECB-as-CTR, HMAC-SHA2, constant-time compare) stays on `System.Security.Cryptography`. Activating ciphers inside the key-exchange orchestrator (rather than returning keys for a caller to apply) keeps the NEWKEYS→cipher-swap invariant in one place, and per-direction cipher instances give each direction its own nonce/counter state without a bidirectional object carrying two responsibilities. Real-OpenSSH interop is deferred to a later checkpoint because it needs `sshd` (absent) or the not-yet-built bam.ssh server (Phase 8); Phase 4 is gated on deterministic loopback round-trips, tamper rejection, and a rekey test instead.

## D-012: authentication is client-only this phase; orchestrator owns the reply loop, methods use a conversation seam; BouncyCastle admitted to `bam.ssh.authentication` for Ed25519; encrypted OpenSSH keys deferred

**Date:** 2026-07-16
**Decision:** Phase 5 implements the **client** side of RFC 4252 in `bam.ssh.authentication` (server-side auth policy is Phase 8). `SshUserAuthenticator` owns the packet loop and handles the generic replies (SUCCESS/FAILURE, and transparently BANNER via `ISshBannerSink`) centrally, while method-specific messages (60–79) are handed to the running `ISshAuthenticationMethod` through the narrow `ISshAuthenticationConversation` seam it implements — so each method (`none`/`password`/`publickey`/`keyboard-interactive`) drives its own sub-dialog and is independently testable, and no two readers race on the not-thread-safe transport. Client private keys are modeled by `ISshPrivateKey` (`Ed25519PrivateKey`/`EcdsaNistP256PrivateKey`/`RsaPrivateKey`), the **signing** counterparts of the transport host-key **verifiers**, emitting the identical `string(alg) ‖ string(sig)` blob; publickey signs the session-id-bound request per §7. `SshPrivateKeyReader` parses OpenSSH v1 (unencrypted) and PKCS#8/PEM (plain or encrypted). BouncyCastle is admitted to `bam.ssh.authentication` (a documented, narrowly-scoped exception to D-001, mirroring D-009) solely for **Ed25519 signing and Ed25519 private-key parsing** — the BCL still has no Ed25519; RSA/ECDSA use the BCL throughout. **Encrypted OpenSSH-v1 keys (bcrypt-pbkdf) and the SSH_MSG_USERAUTH_PASSWD_CHANGEREQ change flow are deferred** — the parser throws a clear `SshAuthenticationException` for encrypted OpenSSH keys, and PASSWD_CHANGEREQ is reported as a failure; encrypted PKCS#8 keys *are* supported (BCL native).
**Why:** Centralizing the generic-reply handling and giving methods a narrow seam keeps each type at one responsibility (open/closed for a future certificate/GSS-API method) and avoids duplicating banner/disconnect handling per method. Making the signers the mirror image of the existing verifiers means a client signature is provably byte-compatible with what a real server runs — the tests verify each publickey signature with the production transport verifiers rather than a bespoke check. BouncyCastle is the only pure-managed, AOT-safe source of Ed25519, and precedent already exists (D-009); confining it to Ed25519 keeps the rest BCL-only. Encrypted-OpenSSH and password-change support are real but self-contained follow-ons (bcrypt-pbkdf is a nontrivial KDF); deferring them keeps Phase 5 scoped while the exception makes the boundary explicit rather than silent. Real-OpenSSH interop remains deferred to Phase 8 (no `sshd`); Phase 5 is gated on the loopback dialog against a server that reuses the production verifiers.

## D-013: connection protocol is client-driven with a single reader/writer; automatic re-keying lives here via a packet-source seam

**Date:** 2026-07-16
**Decision:** Phase 6 implements the RFC 4254 connection protocol in `bam.ssh.connection` (`Bam.Ssh.Connection`). One `SshConnection` owns the authenticated transport and is its **sole reader** (a single receive-dispatch loop) and **sole writer** (every send funnels through one `SemaphoreSlim`-guarded outbound queue), so the not-thread-safe transport is never touched concurrently. Channels are demultiplexed by recipient channel id. A generic `SshChannel` carries data/extended-data over per-stream `System.IO.Pipelines` pipes with the pipe's own back-pressure disabled — the SSH receive window (replenished only as the consumer drains, via `SshReceiveWindow`) bounds buffered memory so a slow channel cannot head-of-line-block the transport; outbound writes are chunked to the peer's maximum packet size and metered by `SshSendWindow`, which asynchronously waits for `CHANNEL_WINDOW_ADJUST`. Session semantics (`exec`/`shell`/`subsystem`/`env`/`pty-req`/`signal`/`window-change`, plus `exit-status`/`exit-signal`) live in `SshSessionChannel`, which **composes** (not inherits) `SshChannel`. **Automatic re-keying (deferred from Phase 4) lives here**: on a byte/time threshold or a peer `KEXINIT`, the loop enters re-key mode, holds the send lock (queuing application traffic), and feeds the key-exchange packets it reads to `SshClientKeyExchange.RekeyAsync` through a new `ISshPacketSource` seam (`SshPacketQueue`) so the loop stays the only transport reader; the existing kex routine is reused unchanged apart from that optional parameter. **Server-side acceptance of inbound `CHANNEL_OPEN` is deferred to Phase 8** (inbound opens raise `ChannelOpenReceived` and are rejected `UNKNOWN_CHANNEL_TYPE`); forwarding channel types (`direct-tcpip`/`forwarded-tcpip`) are Phase 11 — the generic channel already carries their data, only the open-parameter helpers are deferred.
**Why:** A single reader/writer is the only race-free way to multiplex a non-thread-safe byte stream, and it gives automatic re-keying a natural single home (only the loop owner can safely pause application traffic to renegotiate). Tying window replenishment to consumer drain — rather than to receipt — is what prevents one slow channel from stalling every other channel over the shared transport. Reusing `SshClientKeyExchange` via a narrow `ISshPacketSource` seam avoids duplicating the negotiation/exchange-hash/derivation logic already proven in Phase 3–4 tests. Composition of `SshSessionChannel` over `SshChannel` keeps transport-generic channel behaviour and session policy at one responsibility each, so Phase 11's forwarding channels reuse the same `SshChannel` with different open parameters and no session requests. Deferrals are explicit (event + typed rejection reason) rather than silent stubs, per the work-in-progress convention.

## D-014: high-level `SshClient` façade; host-key trust is a pluggable verifier (known_hosts/TOFU default); reuse Phase 5 auth methods; SFTP/SCP/forwarding deferred

**Date:** 2026-07-16
**Decision:** Phase 7 ships `bam.ssh.client` (`Bam.Ssh.Client`) with `SshClient`, an `HttpClient`-shaped façade composing `SshTransport` → `SshClientKeyExchange` → host-key trust → `SshUserAuthenticator` → `SshConnection` behind a *Created → Connected → Authenticated → Disposed* state machine (`ConnectAsync` over TCP host/port or an injected `ISshDuplexStream`; `AuthenticateAsync` + password/publickey convenience; `ExecuteAsync` → `SshCommandResult`; `OpenSessionChannelAsync`/`OpenShellAsync`). **The host-key trust decision deferred by D-010 lands here as a pluggable `ISshHostKeyVerifier`**, checked after key exchange and before any credentials are sent: `KnownHostsHostKeyVerifier` implements real OpenSSH `known_hosts` (plain and `[host]:port` patterns, HMAC-SHA1 hashed `|1|salt|hash` entries, TOFU vs. strict modes, and byte-exact change detection that rejects a differing key as a possible MITM), alongside `CallbackHostKeyVerifier` and the bluntly-named insecure `AcceptAllHostKeyVerifier`. The **default** policy is TOFU known_hosts over `~/.ssh/known_hosts`, matching interactive `ssh`'s first-connect behavior. Authentication reuses Phase 5 `ISshAuthenticationMethod`s directly (thin password/publickey overloads) rather than a parallel credential abstraction. Keep-alive is an optional `keepalive@openssh.com` global-request loop (`SshClientKeepAlive`), disabled unless an interval is set. **SFTP/SCP/port-forwarding client methods (`UploadAsync`/`DownloadAsync`/forwarding) and the full terminal abstraction are deferred to Phases 9–11**; `OpenShellAsync` returns a raw session channel this phase.
**Why:** A single façade is the developer-facing API the directive asks for (HttpClient-like), and threading host-key trust through a narrow strategy keeps the security-critical matching logic swappable and independently testable — the known_hosts tests exercise TOFU/match/changed-key/strict/hashed in isolation without the full stack, which is exactly where a trust bug would hide. HMAC-SHA1 appears only for hashed-host matching because that is the precise construction OpenSSH uses; it obscures which hosts you have visited and is not a security primitive (all real hashing stays SHA-2), a documented interop exception to the "no SHA-1" rule. Reusing the Phase 5 method model (rather than inventing credentials) honors the reuse-existing-infrastructure mandate and keeps auth extensibility in one place. The end-to-end client test chains the already-proven Phase 3/5/6 doubles into one combined server so a single connect→auth→exec call covers the whole stack; TOFU-by-default is documented, with strict/callback one option away and accept-all explicitly insecure.

## D-015: server layer mirrors the client; server host-key signing reuses the client private-key shape; auth is a two-policy seam; inbound channel-open and command dispatch are new seams; real-OpenSSH interop still deferred

**Date:** 2026-07-16
**Decision:** Phase 8 ships `bam.ssh.server` (`Bam.Ssh.Server`) with `SshServer`, the peer of `SshClient`: a configure-then-serve façade composing the **server role** of every layer — `SshTransport` → `SshServerKeyExchange` → `SshServerAuthenticator` → `SshConnection` (with a server channel-open handler) — behind `AddHostKey`/`UsePasswordAuthentication`/`UsePublicKeyAuthentication`/`MapExec`/`MapShell`/`MapSubsystem`, then `StartAsync`(TCP)/`StopAsync` or an injectable `AcceptAsync(ISshDuplexStream)` (the test/embedding seam). Configuration freezes when serving begins. The new pieces land in the layer they belong to, not in the server project: (1) **transport** gains `SshServerKeyExchange` (the mirror of `SshClientKeyExchange` — negotiates, runs agreement on the client's public value, computes and **signs** the exchange hash, advertises only the algorithms of the host keys it holds and selects the matching signer post-negotiation) plus two seams — `ISshHostKeySigner` (the signing peer of the verify-only `ISshHostKey`) and `ISshRekeyDriver` (so `SshConnection` drives re-key with either the client or server exchange); (2) **authentication** gains `SshServerAuthenticator` + `ISshPasswordAuthenticator`/`ISshPublicKeyAuthenticator` policies, and `ISshPrivateKey` now extends `ISshHostKeySigner` so a Phase 5 client private key **doubles as a server host key** with zero new code (the blob encoding is identical); (3) **connection** gains inbound `CHANNEL_OPEN` acceptance (the deferral flagged in D-013) via `ISshChannelOpenHandler` + `SshChannelOpenRequestContext` (Accept/Reject) and `SshChannelRequestEventArgs.Reply(bool)` so a server session answers `exec`/`shell`/`subsystem` with SUCCESS/FAILURE while an unanswered `want_reply` still auto-fails; it also exposes `SshConnection.Completion` and `SshChannel.WriteExtendedAsync` (stderr). `SshServerSession` is the connection's channel-open handler: it accepts `session` channels, maps each `exec`/`shell`/`subsystem` to a mapped `SshServerCommandHandler` run **off the dispatch loop**, and hands it an `SshServerCommandContext` (stdin `ReadAsync`, stdout `WriteAsync`, stderr `WriteErrorAsync`, `ExitAsync`); a returning handler finalizes with `exit-status` 0 (EOF, CLOSE), a throwing one with 1. Publickey requests are verified twice — policy authorization **and** signature check against the session-id-bound §7 blob with the production transport verifier. `SshServerOptions` adds a pre-auth banner and a concurrent-connection cap. **Handshake/auth/idle timeouts and per-user limits are deferred** (only a connection cap ships), and **real-OpenSSH interop remains deferred** — Phase 8 proves our client ↔ our server, not `sshd`.

**Why:** Building each server counterpart *in the layer it mirrors* (kex in transport, auth in authentication, channel-open in connection) keeps every library's role intact and lets the server project stay a thin composition, exactly as the client project is — no layer learns about "server" as a special case beyond the seams above. Making `ISshHostKeySigner` the signing peer of `ISshHostKey`, with `ISshPrivateKey` extending it, means the Phase 5 signers become host keys for free and — more importantly — a server signature is provably byte-compatible with what the client verifies, so the tests check server-signed exchanges with the production client verifier rather than a bespoke path (the same discipline used in D-012 for auth). Driving re-key through the narrow `ISshRekeyDriver` seam lets the one proven `SshConnection` loop serve both roles without duplicating the multiplexing/flow-control/re-key machinery. Running command handlers off the receive-dispatch loop preserves the single-reader invariant (a handler that blocks on I/O cannot head-of-line-block other channels), and answering the channel request *before* spawning keeps the RFC 4254 reply ordering correct. Verifying publickey signatures with the real transport verifier (not just trusting the policy) is the security-critical half of server auth — an authorized key with a forged signature must still be rejected. Deferring timeouts and OpenSSH interop keeps Phase 8 scoped to "the two bam.ssh endpoints interoperate," which the crown-jewel loopback tests (password + publickey + exec stdout/stderr/exit + subsystem streaming + rejection paths) now prove end to end; `sshd`-based interop is a later checkpoint once a server exists to test against.

## D-016: SFTP v3 engine decoupled from the SSH façades via a byte-channel seam; server-side virtual filesystem abstraction with in-memory + path-jailed physical implementations; sync-parse before async

**Date:** 2026-07-17
**Decision:** Phase 9 ships `bam.ssh.sftp` (`Bam.Ssh.Sftp`) — SFTP **version 3** (draft-ietf-secsh-filexfer-02, the OpenSSH-compatible baseline) as a protocol engine, a client, and a server. The engine reads and writes through a one-method-each `ISftpChannel` seam so `bam.ssh.sftp` references only `bam.ssh.connection`: the client wraps an `SshChannel` (`SshChannelSftpChannel`) and the server wraps a served `SshServerCommandContext` (`SshServerCommandContextSftpChannel`, a thin adapter added to `bam.ssh.server`, which already references `bam.ssh.sftp`), with the `subsystem sftp` glue exposed as `SshServer.MapSftp(ISftpFileSystem)` / `MapSftp(Func<SshServerCommandContext, ISftpFileSystem>)`. `SftpMessageChannel` frames the `uint32 length ‖ byte type ‖ payload` records with pooled buffers and an oversized-length guard. `SftpClient` performs the INIT/VERSION handshake then runs a single background reader loop that correlates responses to pending requests by the SFTP `uint32` id (mirroring `SshConnection`'s single-reader discipline), exposing the primitives plus chunked `UploadAsync`/`DownloadAsync`/`ListDirectoryAsync`; a non-`OK` status becomes an `SftpStatusException` carrying the `SftpStatusCode`. `SftpServer` serves one channel from an `ISftpFileSystem`, processing one request at a time with a handle table and turning any filesystem `SftpStatusException` into the matching `STATUS` response (unknown types → `OP_UNSUPPORTED`). `ISftpFileSystem` is the pluggable backing store with two implementations: `InMemorySftpFileSystem` (a dictionary tree, deterministic and sandboxed) and `PhysicalSftpFileSystem` (an OS directory subtree **jailed** to a root — paths are canonicalized so `..` cannot climb above the root, with a defense-in-depth `IsWithinRoot` check, and positional I/O via `RandomAccess`). Because `SshWireReader`/`SshWireWriter` are ref structs that cannot cross an `await`, both client and server **parse each message synchronously into a plain request/response object before doing async work**. **Deferred (documented):** SFTP v4–v6, SYMLINK/READLINK and vendor extended requests (answered `OP_UNSUPPORTED`), and real-OpenSSH interop.

**Why:** Threading SFTP over a narrow `ISftpChannel` (rather than binding to `SshChannel` or the client/server façades) keeps the protocol engine independently testable — the crown-jewel round-trips run the real `SftpClient` over the real `SshClient`↔`SshServer` stack, but the same engine could run over any byte channel — and preserves strict layering (sftp depends only on connection; the server-context adapter lives in the server project that already owns that type). A single-reader id-correlated client is the only race-free way to multiplex request/response over one channel, reusing the exact discipline proven in the connection layer. Making the filesystem a pure async abstraction puts the one security-critical piece — the physical path jail — in a small, unit-testable place and lets a server choose in-memory, on-disk, or a per-user root without touching the protocol code. Canonicalizing paths as the primary sandbox (with `IsWithinRoot` as defense-in-depth) is what actually neutralizes `..` traversal: a Phase 9 test confirms a traversal attempt resolves inside the root and leaks nothing. Parsing synchronously before awaiting is the same ref-struct rule the whole stack follows; doing it once per message into a plain object keeps the async dispatch clean. Deferrals are the directive's standard "document unsupported extensions" call — v3 is the interoperable baseline, and the higher versions/symlinks/OpenSSH interop are self-contained follow-ons.

## D-017: SCP is two symmetric role engines over the Phase 9 filesystem; it rides `exec` of the `scp1` binary protocol; the client's local store is also an `ISftpFileSystem`

**Date:** 2026-07-17
**Decision:** Phase 10 ships `bam.ssh.scp` (`Bam.Ssh.Scp`) — the classic **SCP `scp1` binary protocol** (the wire `scp -t`/`scp -f` still speaks), as a protocol engine, a client, and a server-side handler. The insight the design turns on: SCP is symmetric — whichever side sends file bytes is the **source** and whichever receives is the **sink**, and the one handshake asymmetry collapses because **the sink always sends the first acknowledgement and the source always reads it first**, in both `scp -t` (peer is sink) and `scp -f` (peer is source). So the whole protocol is two role engines reused on both ends: `ScpSender` (source — streams `C`/`D`/`E` records + data from an `ISftpFileSystem`) and `ScpReceiver` (sink — receives records + data into an `ISftpFileSystem` via OpenSSH's directory-stack placement, including the top-level single-file/dir rename). Both ride a one-method-each `IScpChannel` seam, so `bam.ssh.scp` references only `bam.ssh.connection` (+ `bam.ssh.sftp` for the store); the client wraps an `SshChannel` (`SshChannelScpChannel`) and the server wraps a served `SshServerCommandContext` (`SshServerCommandContextScpChannel` in `bam.ssh.server`). `ScpProtocol` owns the byte grammar (single-byte `0x00`/`0x01`/`0x02` acks, newline-terminated control lines, exact-length pooled-buffer data copy). `ScpControlMessage` parses/formats the `C`/`D`/`E`/`T` records; `ScpCommand` parses the remote `scp …` command line (mode `-t`/`-f`, bundled flags, `-r`, `-p`, quoted paths). `ScpClient` opens **one exec channel per transfer** (an scp invocation *is* one `exec`) and exposes `UploadAsync`/`DownloadAsync` for single files and, recursively, directory trees. The server side is `SshServer.MapScp(ISftpFileSystem)` / `MapScp(Func<SshServerCommandContext, ISftpFileSystem>)`, an **exec** handler (SCP has no subsystem name) that parses the command line and runs the matching role engine; a non-`scp` exec is answered with an error and a non-zero exit. The Phase 9 `ISftpFileSystem` is reused verbatim as the backing store on **both** ends — `InMemorySftpFileSystem` for the client's local store in tests, `PhysicalSftpFileSystem` (path-jailed) for on-disk — so no new storage abstraction was introduced. **Deferred (documented):** the modern SFTP-tunneled `scp` (OpenSSH's newer `scp` optionally rides SFTP), remote-path glob/wildcard expansion, and preserve-mode fidelity beyond permissions + mtime/atime (no uid/gid/ACLs), and real-OpenSSH interop.

**Why:** SCP's inherent symmetry means writing the protocol once (two engines) instead of four times (client-up, client-down, server-in, server-out) — client-upload and server-source are literally the same `ScpSender`, client-download and server-sink the same `ScpReceiver` — which halves the surface and lets the crown-jewel tests exercise every path over the real `SshClient`↔`SshServer` stack. Encoding the "sink sends the first ack" invariant in one place is what keeps the handshake from deadlocking; the tests assert full round-trips (a single file and a nested tree, in-memory and on-disk), not just individual sends. Riding `exec` rather than inventing a subsystem is exactly how real scp works, so the client interoperates with a stock remote `scp` and our server answers a stock local `scp`. Reusing `ISftpFileSystem` as the local store (not raw `Stream`s) is what makes recursion clean — directory enumeration and creation already exist and are already jailed and tested — and satisfies the "reuse bamtk infrastructure" mandate: SCP added zero new storage or crypto code. The `IScpChannel` seam mirrors Phase 9's `ISftpChannel` decoupling, preserving strict layering (scp depends only on connection + the sftp store abstraction; the server-context adapter lives in the server project that already references scp). Deferrals are self-contained follow-ons: the traditional binary protocol is the interoperable baseline for `scp -t`/`scp -f`, and SFTP-tunneled scp/glob/extended metadata do not block file copy.

## D-018: forwarding is one socket↔channel bridge with two role engines over the Phase 6 channel/global-request plumbing; connection-layer seams (per-type open handlers, a global-request handler, reply data) make it composable on both roles; server glue mirrors MapSftp/MapScp

**Date:** 2026-07-18
**Decision:** Phase 11 ships `bam.ssh.forwarding` (`Bam.Ssh.Forwarding`) — RFC 4254 §7 TCP/IP port forwarding: **local** (`-L`), **remote** (`-R`), and **dynamic SOCKS** (`-D`). The design turns on the observation that all forwarding is *one bidirectional byte pump* (`SshChannelSocketBridge`, socket on one end, `SshChannel` on the other) plus four wire codecs (`DirectTcpIpChannelRequest`, `ForwardedTcpIpChannelInfo`, `TcpIpForwardRequest` + bound-port reply); the only variation across modes is which side owns the listener and which owns the `connect`. So the connect side is a reusable `ISshChannelOpenHandler` (`DirectTcpIpChannelAcceptor` for the server's `-L`/`-D`; a per-connection `ForwardedTcpIpChannelAcceptor` for the client's `-R`) and the listen side is a small `IAsyncDisposable` (`LocalPortForwarder`/`DynamicPortForwarder` on the client, `TcpIpForwardListener` on the server). The forwarding project references only `bam.ssh.connection`; the server-context glue (`SshServer.EnableTcpForwarding` + `SshServerForwarding`) lives in `bam.ssh.server` exactly as `MapSftp`/`MapScp` do, and `SshClient` gains `Forward{Local,Remote,Dynamic}PortAsync`. **Three connection-layer seams (the open-parameter/global-request helpers D-013 deferred to this phase) make it composable on both roles without changing how a connection is constructed:** (1) per-channel-type open-handler registration (`RegisterChannelOpenHandler`), checked before the constructor fallback, so the **client** can accept inbound `forwarded-tcpip` (it has no fallback handler) and the **server** can accept `direct-tcpip` *alongside* its `session` handler; (2) an `ISshGlobalRequestHandler`/`SshGlobalRequestContext` seam so a server services `tcpip-forward`/`cancel-tcpip-forward` (unregistered names still auto-fail); (3) global-request reply data (`SendGlobalRequestWithReplyAsync` → `SshGlobalRequestReply`) so a port-0 `tcpip-forward` reads the server-chosen bound port from `REQUEST_SUCCESS`. Dynamic forwarding speaks SOCKS5 (no-auth) and SOCKS4/4a CONNECT via `SocksNegotiator`. Every pump is fault-contained so a broken tunnel never faults the shared `SshConnection`. **Deferred (documented):** X11/agent/StreamLocal forwarding, SOCKS BIND/UDP and SOCKS5 auth beyond no-auth, `SSH_OPEN_CONNECT_FAILED` fidelity (a server connect failure surfaces as an immediate channel close because the open handler must not block the dispatch loop — it accepts, then connects off-loop), and real-OpenSSH interop.
**Why:** Writing forwarding as one bridge + two role engines (rather than four socket-pumping code paths) is the same leverage SCP's symmetry gave Phase 10 — client-local-listen and server-remote-listen share `TcpIpForwardListener`'s shape, client-`-L`-connect and server-`-R`-connect share the acceptor shape, and every half-flow reuses the one bridge, so the crown-jewel tests exercise all of it over the real `SshClient`↔`SshServer` stack against real TCP echo targets. Putting the three seams in the **connection** layer (not the façades) is what lets both roles accept peer-initiated channels/requests: the client needs to accept `forwarded-tcpip` with no server session, and the server needs `direct-tcpip` in addition to `session` — a single composite handler baked into either façade could not express that, whereas a per-type/per-name registry can, and it keeps the one proven single-reader/single-writer `SshConnection` unchanged apart from additive dispatch. Making the global-request reply carry data is the minimal change that unblocks port-0 remote forwarding (the RFC's one place a global-request success returns a value). Routing inbound `forwarded-tcpip` by connected port through one shared per-connection acceptor lets several `-R` forwards coexist on a connection (only one handler may be registered per channel type). Reusing raw `Socket`s + the existing channel flow-control (not a new stream abstraction) keeps the bridge allocation-light and honors the reuse mandate — forwarding added zero new transport, crypto, or storage code. Fault-isolating every pump preserves the connection invariant that one misbehaving channel cannot take down the multiplexed transport. The deferrals are self-contained follow-ons: `direct-tcpip`/`forwarded-tcpip`/`tcpip-forward` are the interoperable core of `-L`/`-R`/`-D`, and X11/agent/StreamLocal/SOCKS-auth do not block TCP forwarding.
